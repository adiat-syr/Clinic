# База данных и транзакционное ядро — этапы 2–3

Актуально на 05.11.2026. PostgreSQL **18.6**, Prisma CLI/client/adapter **7.10.1**. Этап 3 добавляет auth/MFA/RBAC и catalogue/staff/audit HTTP API; UI и booking/schedule HTTP пока отсутствуют. Юридические и production-условия README остаются открытыми. Авторизация, протокол и минимальные права: [AUTH.md](AUTH.md).

## Модель и миграции

Источник декларативной модели — `apps/api/prisma/schema.prisma`. 13 моделей сопоставлены SQL-таблицам README: 11 моделей этапа 2 (сотрудники, сессии, врачи, услуги, назначения врач–услуга, рабочие интервалы, записи, версии согласия, доказательства принятия, ключи повторов, аудит), а также одноразовый bootstrap marker и общие rate-limit buckets этапа 3.

- UUID PK; составной PK назначений; составной FK записи на назначение. Все FK — RESTRICT, без потери истории каскадным удалением.
- Timestamps — `timestamptz(3)`, интервалы — абсолютные моменты времени, ISO-вход обязательно с UTC/offset. Преобразование даты/времени клиники для UI/API остаётся последующему этапу; сервер не использует локальную зону ОС для вычисления интервала.
- Деньги — `numeric(12,2)`/Prisma Decimal; сериализация десятичной строкой. Цена конечная, от 0 до 9 999 999 999.99; PostgreSQL `NaN` также отклоняется. Длительность 1–1440 минут. Запись хранит собственные цену/длительность и точный `ends_at`.
- Контакты — nullable `bytea` с версией ключа. CHECK допускает полный зашифрованный комплект либо полный NULL-комплект с `anonymized_at`. Сервис создания требует запечатанный комплект; настоящие контакты не используются.
- Индексы: все FK покрыты ведущими колонками B-tree/PK, плюс выборки врача/даты, статуса/даты, сроков технических записей и аудита. Это проверяется запросом к каталогам PostgreSQL, а не только текстом schema.

Миграции:

1. `20261104000100_initial` — сгенерированные Prisma таблицы, enum, FK и индексы, обёрнутые в SQL-транзакцию.
2. `20261104000200_integrity` — ручные CHECK, `btree_gist`, exclusion constraints, частичный unique текущего согласия и триггеры. Применяется транзакционно.
3. `20261105000100_staff_security` — singleton bootstrap marker с RESTRICT FK и immutable UPDATE/DELETE, rate-limit hash/counter/expiry CHECK и индекс, trigger отзыва сессий при смене доступа/credentials. Старые миграции не изменены.

`appointments_no_overlap` исключает пересечение `tstzrange(starts_at, ends_at, '[)')` одного врача для **всех статусов, кроме CANCELLED**. Оно защищает и от разных длительностей, и от прямого SQL, и от нескольких процессов. Соседние приёмы разрешены. `availability_no_overlap` не разрешает перекрывать рабочие интервалы одного врача; рабочий интервал имеет конечные границы и длину до 24 часов. В сервисе границы рабочих интервалов должны быть кратны минуте.

Опубликованный текст согласия/хеш/версия не меняются; разрешено однократное снятие с публикации. Одновременно может быть только один неархивный документ. Доказательство согласия неизменяемо, кроме однократной фиксации отзыва. Отложенные constraint triggers не позволяют завершить транзакцию с записью без доказательства согласия. Аудит защищён от UPDATE/DELETE; metadata — JSON object до 2048 bytes. Этап 3 пишет пустой объект или allowlist имён изменённых полей, без значений/контактов.

**Не изменять уже применённые миграции.** Новые изменения оформлять следующей миграцией и прогонять весь integration suite: он применяет полную историю и проверяет ручные ограничения. Prisma schema не описывает все CHECK/trigger/exclusion; `db push`/reset не заменяют миграции. Ограничения, не отражённые ORM, нельзя удалять при последующих изменениях.

## Транзакционный протокол

Внутренний `BookingService` не является HTTP API. Он получает Prisma client, устойчивый серверный HMAC-ключ и policy/clock. Реализованы расчёт свободных интервалов, создание, изменение рабочих окон, перенос, смена статуса и координируемые деактивации/изменения услуги.

Порядок блокировок:

```text
Создание: advisory xact lock ключа повтора
          → врачи по UUID → услуги по UUID → согласие FOR SHARE → запись/согласие/ключ
Перенос: исходный и целевой врачи по UUID → услуги по UUID → запись FOR UPDATE
Статус: врач → услуга → запись FOR UPDATE
Расписание/деактивация врача: врач FOR UPDATE
Назначение услуги: врач → услуга
Изменение цены/длительности/активности услуги: только услуга; затем врачей не захватывать
```

Все блокировки принадлежат PostgreSQL и освобождаются при commit/rollback; нет mutex процесса. Изменение расписания и создание записи координируются одной строкой врача. READ COMMITTED даёт новые снимки после ожидания блокировки. Идемпотентность проверяется до текущей доступности/активности: повтор уже успешного запроса не становится ошибкой занятого времени.

В этапе 3 HTTP catalog service использует общие `catalog-mutations` вместо отдельного неконтролируемого ORM-write. Проверка staff/session и изменение каталога входят в одну транзакцию: для управления сотрудниками сначала management advisory lock, затем сотрудники по UUID → сессия → указанный выше doctor/service протокол. Bootstrap использует ту же management-блокировку. Порядок существующего ядра бронирования не менялся; безопасная композиция auth и HTTP booking-транзакций — часть будущего этапа 4.

Короткие Prisma interactive transactions: maxWait 15 s, timeout 10 s, SQL lock_timeout 5 s и statement_timeout 6 s. Только 40001/40P01/55P03 и соответствующие классификации Prisma повторяются — максимум 3 попытки с короткой задержкой. После исчерпания — `CONCURRENCY_RETRY_EXHAUSTED`. Не повторять произвольные ошибки соединения/коммита автоматически. Внешних HTTP-вызовов и побочных действий вне БД внутри транзакций нет.

Основания протокола: [Prisma 7 interactive transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions), [PostgreSQL 18 READ COMMITTED](https://www.postgresql.org/docs/18/transaction-iso.html), [row/advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html). Exclusion constraint — по [range constraints PostgreSQL 18](https://www.postgresql.org/docs/18/rangetypes.html#RANGETYPES-CONSTRAINT).

Повтор запроса: SHA-256 ключа с namespace, HMAC канонических параметров, транзакционная advisory-блокировка хеша и unique PK в таблице. Ключ — hex минимум 16 случайных байт. Технический TTL 24 часа; существующий просроченный ключ отклоняется как `IDEMPOTENCY_EXPIRED`. Совпавшие ключ/параметры возвращают тот же reference и актуальное безопасное состояние. Неподходящий payload — `IDEMPOTENCY_CONFLICT`. При ошибке последней записи ключа откатываются и запись, и согласие.

Цена и конец интервала вычисляются из активной услуги. Весь приём должен помещаться в **одном** рабочем интервале, с шагом начала относительно его начала; перерыв нельзя пересекать. Предварительная policy: шаг 15 минут, минимум 60 минут до приёма, горизонт начала 60 суток; параметры требуют согласования клиники. Доступность — расчёт, без таблицы фиктивных свободных слотов.

Перенос проверяет version, блокирует обоих врачей в одном порядке, обновляет одну строку и snapshots, сбрасывает статус в PENDING. Неудача сохраняет исходную запись. Сокращение/удаление рабочего интервала запрещено, если будущая или ещё продолжающаяся неотменённая запись окажется вне оставшихся интервалов.

Переходы: PENDING → CONFIRMED/CANCELLED; CONFIRMED → COMPLETED/NO_SHOW/CANCELLED. Подтверждение — до начала, завершение/неявка — после окончания; терминальные статусы не открываются. Любая смена статуса/перенос увеличивает version. Деактивация каталога не отменяет существующие записи и не переписывает их snapshots.

## Граница персональных данных

`SealedContacts` — **доверенный внутренний контракт**, не схема публичной формы. В нём ciphertext, key version и стабильный серверный fingerprint контактов. Последний используется внутри HMAC запроса, но не сохраняется отдельной колонкой. Он позволяет безопасно повторить запрос с новым nonce шифрования. Будущий HTTP-handler обязан сам получить эту структуру от privacy-модуля; не принимать fingerprint или ciphertext из тела публичного запроса.

Production-проверка имени/телефона, их нормализация, шифрование/ротация/хранение ключей и юридическая пригодность выбранных криптосредств ещё **не реализованы**. Только test helper использует AES-GCM с одноразовым ключом в памяти и явно синтетические значения. Этот helper не подключён к приложению. Возвращаемый сервисом объект содержит internal id для orchestration; будущий public controller должен выбрать только разрешённый DTO, а не вернуть объект целиком.

Доменный код `SLOT_UNAVAILABLE` маппится только для конкретного `23P01 / appointments_no_overlap`; `availability_no_overlap` даёт `SCHEDULE_OVERLAP`. Unique errors классифицируются отдельно. Соответствие проверено на фактическом PrismaPg adapter, без выдачи SQL/parameters/message наружу. Этап 3 подключает безопасный HTTP mapper (в частности DUPLICATE_RESOURCE → 409), RBAC и каталог. `/appointments` по-прежнему 404 до этапа 4.

## Локальные команды

Из корня после `npm ci` и `npm run setup`:

```sh
npm run db:up
npm run db:generate
npm run db:validate
npm run db:deploy
npm run db:seed
npm run db:check
npm run test:integration
npm run dev
```

`db:deploy` не выполняет reset и seed автоматически. `db:seed` ограничен synthetic local development/test, генерирует Prisma Client и запускает seed. Первый запуск добавляет только 2 вымышленных врача, 3 услуги, 6 назначений, 4 интервала с перерывом, тестовое согласие и отключённого сотрудника `example.invalid`. **Нет пациентов, записей и действующего пароля ADMIN.** Повторный запуск не перезаписывает существующие fixtures, цены и интервалы. Рабочие интервалы первого запуска формируются на следующий UTC-день; seed не переносит старый календарь автоматически.

Доступность local health сама не проверяет миграции или готовность всех API. Обновлённый smoke дополнительно читает public catalogue и проверяет admin 401 через Vite proxy; ему нужны deploy и seed. Для production по-прежнему нужны отдельные роли БД, договоры, размещение в Казахстане и согласования README.

## Безопасность интеграционных тестов

`npm run test:integration` генерирует client, затем runner:

1. Проверяет synthetic mode, local host и PostgreSQL 18.6.
2. Создаёт собственную БД `clinic_test_<32 hex>`; на рабочей БД не выполняются reset/truncate/drop.
3. Дважды запускает `prisma migrate deploy`: сначала с нуля, затем no-op.
4. Передаёт тестам отдельный URL через окружение, без файла с credentials. Разрушающие fixture-операции дополнительно проверяют имя тестовой БД и совпадение URL.
5. После тестов закрывает/завершает только соединения этой БД и удаляет именно её. Имя не принимается от пользователя.

Нужен локальный PostgreSQL-пользователь с CREATEDB; bootstrap-пользователь Compose/CI это позволяет. В production приложение такого права иметь не должно. В CI та же команда разворачивает временную БД внутри отдельного service-container; workflow не публикует приложение. При принудительном завершении процесса ОС cleanup не гарантируется — остаточную `clinic_test_*` следует проверять адресно, не удаляя все БД по маске.

## Непроверенное и границы гарантий

- Exclusion/FK/CHECK/согласие/append-only защищены БД. Активность каталога, рабочие окна, policy, версии и переходы статусов координирует **сервис**. Произвольный административный SQL может обойти эти бизнес-правила; будущие handlers должны вызывать сервис, а runtime-роль — иметь минимальные права. Это не система, в которой любые прямые записи администратора безопасны автоматически.
- Auth/MFA/RBAC, CSRF, общие rate limits, audit actor из сессии и catalogue HTTP DTO/409 реализованы на этапе 3; границы production-проверок — в AUTH.md и STAGE-3-REPORT.md. Booking/schedule HTTP и production privacy ещё не подключены.
- Не проверялись production-нагрузка, failover, разрывы сети около commit, RPO/RTO, backup/restore и ротация ключей. Проверены реальные конкурентные операции и инъекции SQLSTATE, без имитации реального кластера.
- Очистка просроченных ключей/сессий/rate-limit buckets, обращения об отзыве согласия, purge/обезличивание и retention ещё не реализованы. Append-only audit требует отдельной контролируемой процедуры удаления по утверждённой политике; SQL owner может TRUNCATE/drop, поэтому триггер не заменяет права.
- Клиническая пригодность назначений врач–услуга, длительности/цены, timezone, юридические тексты и production-инфраструктура не подтверждены. Согласие seed намеренно непригодно для реальных пациентов.

Реальные данные не подключать. Дизайн Stitch и frontend не изменяются. После этапа 3 требуется подтверждение этапа 4.

## Дополнение этапа 4

Booking/schedule HTTP подключены через BookingHttpService и существующий BookingService.inTransaction: staff/session locks, затем прежние doctor/service/appointment locks и audit actor в одном commit. Public create сохраняет idempotency advisory lock первым. Самостоятельные вызовы core по-прежнему открывают собственную транзакцию с прежними retries/timeouts. Новых моделей/миграций этап 4 не требует; все 3 миграции и 13 моделей сохранены. Предыдущие указания «booking HTTP пока 404» в описании этапов 2–3 являются историческими.

Контакты HTTP шифруются ContactPrivacy, раздельные versioned keys и HMAC в окружении; syntheticContacts остаётся только fixture и к runtime не подключается. Отзыв согласия увеличивает version, сохраняет доказательство и статус записи; purge/retention не выдумываются. Подробный контракт и ограничения — BOOKING-API.md. После этапа 4 требуется подтверждение этапа 5.
