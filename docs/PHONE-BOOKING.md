# Дополнительная запись сотрудником по коду согласия

Процесс согласован пользователем в дополнение к этапу 6. **Только синтетический MVP. Юридическая применимость и идентификация не проверены; реальные пациенты запрещены.** Основной способ остаётся прежним: самостоятельная онлайн-запись `/ru/booking` или `/kk/booking`.

## Процедура

1. При телефонном обращении сотрудник объясняет доступные способы и сообщает адрес `/ru/phone-consent` или `/kk/phone-consent`. Это общая ссылка, без контактов/кода/идентификаторов в URL. SMS/email-сервис не подключён. Сотрудник не заполняет форму от имени пациента.
2. Посетитель самостоятельно открывает страницу, читает конкретную опубликованную RU/KK версию, вводит только синтетические имя/телефон и отдельно подтверждает согласие. Галочка не предустановлена. Отказ/неподтверждение не создают ни запись, ни согласие в БД.
3. Сервер сохраняет неизменяемое подтверждение с documentId, locale, acceptedAt, expiresAt и зашифрованными контактами. Создаёт криптографически случайный 128-битный код (32 hex-символа). **Только SHA-256 с доменным префиксом хранится в БД**, открытый код возвращается один раз посетителю и остаётся в памяти страницы. Срок ровно 5 минут по серверным часам. Код не подтверждает личность и не резервирует слот.
4. Посетитель сообщает код сотруднику. ADMIN или RECEPTIONIST открывает «Создать запись по коду пациента», выбирает врача/услугу, дату и реальный свободный слот, вводит код. Эта форма не содержит имени/телефона/«согласен» и не позволяет переопределить сведения пациента.
5. API в транзакции проверяет сессию/MFA/роль и CSRF, вызывает существующее booking core. Оно повторно проверяет действующий документ, время и цену/длительность, срок/одноразовость кода и ограничения расписания. Создаются PENDING приём, обычное AppointmentConsent с исходным acceptedAt пациента, idempotency key, связь потреблённого подтверждения и аудит сотрудника. Слот занимают те же appointments/exclusion constraints, что и онлайн-записи.
6. Сотрудник сообщает результат; PENDING разбирается по обычному процессу. Если время заняли, вся транзакция откатывается, код не расходуется: можно выбрать другое время до истечения 5 минут. Если код истёк, использован, неверен или версия согласия уже сменилась, нужен новый самостоятельный шаг посетителя.

Если посетитель не может/не хочет подтвердить согласие этим способом, программная ручная запись не создаётся. До юридически утверждённой альтернативы нельзя подставлять галочку сотрудника, записывать устное «да» как WEB_CHECKBOX, обходить API или ссылаться на непроверенное исключение из закона. Записи разговоров, ИИН, диагнозы, медицинские документы, вложения и свободные заметки не добавлены.

## API и транзакции

- `POST /api/v1/patient-consent-codes`: strict `{contacts:{name,phone},consent:{documentId,locale,accepted:true}}`, Origin/CSRF, 6/IP/15 минут и общий лимит. Любая staff session cookie приводит к 403 `PATIENT_ACTION_REQUIRED`. Ответ 201 `{code,expiresAt,documentVersion}`, `no-store`. Нет публичного GET поиска/проверки кода и нет публичного чтения записи.
- `POST /api/v1/admin/appointments`: обе роли с полным MFA, strict `{doctorId,serviceId,startsAt,expectedPriceKzt,expectedDurationMinutes,consentCode}`, CSRF/Origin и Idempotency-Key. Контакты, галочка согласия, роли, snapshots, acceptedAt/expiry от клиента отклоняются. 201 новая запись; 200 только идентичный транспортный повтор ранее закоммиченной операции. Ответ как у существующего public booking, без контактов/кода.
- Код нельзя употребить для второй записи: другая попытка/ключ отклоняется 409. Идемпотентный replay одного key + того же payload **не потребляет код повторно**, а возвращает существующий результат даже после истечения пяти минут (в пределах срока idempotency). Это нужно при потере ответа после commit. Изменённый payload с прежним key отклоняется; ответ не является фиктивным успехом.
- Общий порядок: auth staff/session locks → booking idempotency advisory → врачи UUID → услуги UUID → документ согласия SHARE → receipt row FOR UPDATE → запись/согласие/потребление/audit. Другие операции не захватывают врачей после receipt. Данные подтверждения читаются предварительно без lock только для передачи запечатанных контактов; окончательная проверка и потребление происходят под row lock в core. Нет внешних вызовов внутри транзакции.
- Миграция добавляет `patient_consent_receipts`, FK/индексы/unique appointment, exact lifetime и consumption CHECK, immutable evidence trigger. Существующие миграции и exclusion constraints сохранены. Enum ConsentMethod остаётся WEB_CHECKBOX: реальное согласие действительно дано пациентом на отдельной веб-форме. Признак дополнительного процесса — связь receipt и событие `STAFF_APPOINTMENT_CREATED`, не ложное согласие сотрудника.

## Ограничения доказательств и хранения

У администратора нет API/поля для выдачи согласия от имени пациента; из его сессии создание кода блокируется. Однако анонимная веб-форма **не доказывает личность** и технически не отличает пациента от сотрудника, открывшего другой неавторизованный браузер. Это ограничение нельзя устранить текстом инструкции или дополнительным checkbox; реальный процесс требует юридической проверки, контролей личности/полномочий и организационного запрета имитации. Подтверждение телефона/ЭЦП/внешние сервисы в этом объёме не внедрялись.

Код отсутствует в URL, БД plaintext, аудитах, логах, localStorage/sessionStorage. Контакты выдаются только в обычной защищённой карточке с audit. Новый grant содержит ещё одну копию зашифрованных контактов: до production обязателен регламент очистки неиспользованных/использованных подтверждений, backup и удалений с учётом FK. **Истечение кода не удаляет строку автоматически.** Не назначаем юридический срок хранения техническим TTL.

Правовая отправная точка — [статьи 7–8 закона РК о персональных данных](https://old.adilet.zan.kz/rus/docs/Z1300000094): способ должен позволять подтвердить получение согласия. Это не заключение о соответствии конкретной реализации. До реальных данных требуется закрыть [STAGE-7-BLOCKERS.md](STAGE-7-BLOCKERS.md).
