# Эксплуатация и восстановление

Команды выполняются из checkout: `node infra/deploy.mjs INSTANCE ACTION MODE`, MODE staging|production. Production actions требуют отдельного разрешения в окружении; реальные данные не использовались в проверках. Правовые основания/сроки уведомления централизованы в LEGAL-REVIEW-REQUIRED.md (L5–L8).

## Ежедневный контроль

`status`, `logs`, `monitor`: контейнеры healthy, API readiness, PG запрос, очередь старых PENDING, всплеск неуспешных входов, валидность TLS/оставшиеся дни, свежесть успешного backup, целостность deletion ledger и replay. Monitor пишет только агрегаты в приватный `BACKUP_DIR/monitor.json`, при тревоге exit2; scheduler — структурированные события/heartbeat. В HTTP/proxy нет body/header/access logging с PII. Не включать SQL statement/parameter logs для данных записи. SQL ошибка не должна раскрыть DETAIL с email.

Настройки compose.env: BACKUP_INTERVAL_SECONDS (default86400), MONITOR_INTERVAL_SECONDS (default60), CERT_WARNING_DAYS(default7). Для оповещения использовать локальный supervisor/self-hosted collector на выбранной площадке: наблюдать exit2/event `operational_alert`, `backup_scheduler_failure`, `privacy_replay_failure`, `heartbeat_write_failed`, недоступность хоста и Docker health. Автоматической отправки во внешние SaaS нет. Установить ответственного и проверить доставку тревоги до допуска реального трафика. Одного зелёного Docker heartbeat недостаточно — он показывает жизнь scheduler, не успех backup.

Для независимого запуска supervisor приложены `infra/systemd/clinic-monitor@.service/.timer`; установить только на выбранном сервере с корректными User/WorkingDirectory и environment. Проверить его исполнение и OnFailure/локальный канал владельца; systemd на Windows не запускался. Хостовая доступность и заполнение диска также требуют supervision вне самого Docker хоста.

## Backup и ключи

`backup`: pg_dump18 читает readonly-ролью консистентный экспортированный MVCC snapshot, integrity counts из того же snapshot. Dump шифруется AES-256-GCM с независимым backup key, ciphertext копируется в SECONDARY_BACKUP_DIR; fsync и SHA256, HMAC manifest связывает counts, source DB, hash архива и prefix deletion ledger. Plaintext temporary удаляется. Архив/manifest/независимый checkpoint и старые ключи нужны вместе. Status хранит последний успех/ошибку. Автоматический scheduler запускает backup с настраиваемым периодом.

Retention в `config/retention.json` по умолчанию `approved:false`, никакого удаления данных или архивов. Значения — технические параметры, не сроки «по закону». После внешнего утверждения указать decisionReference и сроки/правила. Backup rotation очищает обе копии только согласно включённой политике. Ledger с доказательствами удалений/отзывов не удалять при ротации архивов: он нужен для старых backups. Само checkpoint storage должно быть независимым и защищённым от rollback вместе с primary. Администратор, владеющий хостом/всеми ключами/обеими копиями, находится внутри trust boundary.

Keys файлы приватны и отдельно от БД. Контакты CONTACT_KEYS_JSON, MFA AUTH_MFA_KEYS_JSON, backup BACKUP_KEYS_JSON, ledger DELETION_LEDGER_KEYS_JSON — versioned rings. Ротация: добавить случайный независимый32byte key под новым ID, сохранить старые, изменить активную версию в compose.env; обновить mounts/restart. `rotate-keys` переворачивает contacts/MFA идемпотентно, MFA rotation отзывает сессии; `ledger-rotate-key` перезаписывает подпись registry/checkpoint активным ledger key без изменения encrypted entries/prefix. Новые backups используют активный backup key, старые читаются соответствующим retained ID. Не удалять legacy MFA key до перевода legacy envelopes, ключи старых архивов/entries — до завершения их срока и проверки restore. HMAC/CSRF keys независимы; смена CSRF принудит клиентов получить новый csrf, HMAC смена требует отдельного окна и истечения старых идемпотентных попыток. Ротация паролей PG — контролируемый ALTER ROLE с обновлением соответствующего secret, не повторный bootstrap.

## Проверенный restore и cutover

1. Изолировать инцидент, остановить запись изменений. Проверить хранилища/ключи и актуальность **обеих** копий ledger. Скопировать archive+manifest в BACKUP_DIR без изменения имён. Если потерян один checkpoint, `ledger-reconcile` допускает только аутентифицированный общий prefix, восстанавливает свежую копию; fork/повреждение отклоняются. Не создавать новый пустой ledger поверх истории.
2. `restore ARCHIVE.gcm clinic_restore_<32hex>` восстанавливает только в **новую** отсутствующую БД; существующая БД не удаляется. Проверяет manifest/MAC/ciphertext/ledger до CREATE DB, затем полную GCM authentication до pg_restore. Ограничивает CONNECT, сверяет PG/schema/counts/overlap, повторяет удаления и отзывы, отзывает все сессии и блокирует старые staff credentials. Пример: `node infra/deploy.mjs INSTANCE restore MODE archive.gcm clinic_restore_0123456789abcdef0123456789abcdef` (заменить synthetic имя новым32hex).
3. Target остаётся закрыт runtime. Приёмка восстановленных synthetic/in-scope данных владельцем; выбрать cutover окно. `DATABASE_CUTOVER_APPROVAL=I_APPROVE_DATABASE_CUTOVER` и `restore-finalize TARGET`: deploy останавливает API/scheduler; под общим ledger lock исходная DB `ALLOW_CONNECTIONS false`, её соединения завершаются, latest ledger повторяется на target, staff повторно quarantined, проверяются ограничения, применяются узкие GRANT. Только затем открывается CONNECT target.
4. Обновить pathname БД в runtime/operator/maintenance/backup/migrator secrets (и bootstrap_url для дальнейшего provisioning, сохранив `/postgres` control path внутри restore). Пароли/роли прежние. Не путать source/target. Перезапустить с целевыми URL, убедиться в ready/monitor; source остаётся fenced. Старые staff credentials **не** оживают: восстановление ADMIN только через offline `staff recover-admin`, остальных credentials после проверки владельцем. Не менять bootstrap marker руками.
5. После сбоя finalization target fail-closed. В частности, crash после durable `finalized:true` receipt до GRANT может оставить source fenced и target закрытым. Простой повтор откажет. Безопасный путь — **новый target restore и finalize** от того же исходного архива с текущим ledger; не снимать CONNECT запрет вручную и не удалять signed receipt. Новый target не удаляет failed target/source. После успешной передачи владелец отдельно решает судьбу старых БД.

Stale `registry.lock` после аварии не снимается автоматически. Остановить API/scheduler/все one-off операции, убедиться в отсутствии процесса-владельца, сохранить incident evidence, сверить primary/checkpoint, только затем контролируемо удалить **конкретный lock-файл**, выполнить ledger-reconcile/privacy-reconcile и monitor. Это аварийная процедура, не штатный cron. Не откатывать registry+checkpoint вместе из старого snapshot: это уничтожит информацию о более поздних удалениях.

RPO определяется периодом backup и независимо сохранённым актуальным ledger, RTO — размером БД/каналом/проверкой/перевыдачей staff доступа. Локальный drill на маленьких synthetic данных не подтверждает договорный RPO/RTO сервера.

## Хранение, запросы и удаление

ADMIN фиксирует проверенный отзыв через карточку. До ответа успеха encrypted allowlisted withdrawal intent (appointment/document/time/actor/request) fsync записывается в независимый ledger/checkpoint; ошибка записи даёт503 без DB commit. Если SQL transaction откатился после intent, `privacy-reconcile` повторяет intent идемпотентно, аудитирует и сохраняет attribution. Он не удаляет контакты автоматически. Отзыв не отменяет приём. Очередь обращений и проверка личности — ответственному; не просить ИИН в форме записи.

`cleanup` без approved policy dry-run. При включении очищает истёкшие sessions/rate/idempotency, просроченные unclaimed receipts по заданному сроку и контакты terminal appointments по утверждённым правилам. `anonymize UUID WITHDRAWAL|RETENTION` требует допустимое основание в БД и policy. Операция удаляет имя/телефон/key version и дублирующий receipt, пишет durable encrypted intent и audit; история booking/consent без контактов остаётся. Это минимизация, а не доказательство полной необратимой анонимности: reference/даты/doctor и внешние сведения могут обеспечивать связывание. HMAC fingerprints и технические identifiers также требуют retention review. Staff/audit/consent документы не уничтожаются произвольно.

## Инцидент

Сразу зарегистрировать время обнаружения/ответственного в защищённом канале, отключить затронутый вход/узел без уничтожения evidence; не помещать dump/секреты в тикеты. Отозвать сессии/скомпрометированные credentials, сохранить безопасные агрегаты/хэши артефактов и журнал действий. Проверить объём, source/cutover/ledger, ключи и доступ поставщиков. Восстанавливать из аутентифицированного backup с latest privacy replay и карантином. Возвращать доступ после проверки причины/исправления и повторных негативных тестов. Срок/канал обязательных уведомлений — действующее правило и назначенные лица из LEGAL-REVIEW-REQUIRED.md L6; ориентир уведомления органа **один рабочий день от обнаружения** по статье25(2)(8), не универсальные72часа. Юридические решения/применимость вести только в юридическом файле. Проверить delivery уведомления и сохранять доказательство у клиники.
