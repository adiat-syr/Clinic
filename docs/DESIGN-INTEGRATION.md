## Правила визуального переноса

- Приоритет: явные ограничения пользователя → реальная логика/доступность → токены HTML и YAML DESIGN → декоративные рекомендации prose DESIGN. Это устраняет противоречия внутри самого референса.
- Основной CTA `#005454`, hover/container `#0d6e6e`, белые карточки `#ffffff`, публичная поверхность `#faf8ff`, мягкие блоки `#f2f3ff`/`#eaedff`, основной текст `#131b2e`, вторичный `#3e4948`, turquoise `#6df5e1`. Admin canvas — `#f8fafc`. Не заменять их произвольной новой темой.
- Проза DESIGN дополнительно называет primary `#0D6E6E` и фон `#F8FAFA`, но HTML/PNG используют более тёмный CTA и лавандовый canvas. Для воспроизведения экранов выбрать значения из HTML/YAML; `#0d6e6e` остаётся container/hover.
- Заголовки: Plus Jakarta Sans 600–700, основной текст/формы/цифры: Inter 400–700; шкала display 48/56, mobile 34/42, headline 36/44 или 26/34, body 16/26 и 14/22. Числа — tabular-nums. На PNG часть кириллицы отрисована serif fallback: это не отдельная заданная гарнитура. Для символов ru/kk использовать явный Inter fallback с нужным покрытием, проверив его при финальной UI-приёмке.
- Шрифты поставляются локально с лицензиями; Google Fonts/Material Symbols CDN и Tailwind CDN в приложение не переносить. Иконки — локальный SVG-набор на этапе UI. Внешние изображения и карту не hotlink-ить.
- Радиусы: базовые controls 8–12 px, карточки 16–24 px, чипы pill; не унифицировать всё одним радиусом. Spacing 4/8/16/24/40/64 px, мобильный gutter 16–20 px. Сетка desktop до 1440 px, мобильная колонка, tablet 2 колонки там, где это помогает.
- На mobile сохранить нижнюю навигацию из 5 пунктов: главная, услуги, врачи, запись, контакты, учесть safe area и место под CTA. На desktop — верхняя навигация. Sticky элементы не перекрывают поля/фокус.
- Сохранить характер карточек/композицию, но исправить font-size 11–12 px в важных полях, маленькие touch targets и запрет масштабирования `user-scalable=no`. Минимальная цель управления — 44 px; видимый focus, labels, текстовые статусы и reduced-motion.

Оригиналы остаются неизменными для сравнения. Исправления вносятся в будущий React/UI/API, а не косметической правкой устаревших дат в HTML.

## Единый источник данных

```text
PostgreSQL services + doctors + doctor_services + availability_windows
              ↓ repositories → services → public/admin DTO
REST API → TanStack Query → карточки / прайс / booking / admin
POST appointments → транзакция → snapshots условий записи
```

В карточке врача цена появляется только вместе с явно выбранной услугой. Если услуги несколько — показать список или «от» как вычисленный минимум активных назначений, без придуманной «цены врача». Цены/длительности PostgreSQL не копируются в frontend и не подменяются fallback-массивом при ошибке API. Справочный каталог и исторические snapshots имеют разные назначения. Часовой пояс/контакты/локализация — конфигурация, медицинские данные не собираются.

В этапе 1 **каталога и записи ещё нет**: только контракт health, стартовый экран без формы, проверка подключения к БД. Не показывать демонстрационные слоты или ложное «Запись создана» для видимости готовности.

## Последовательность интеграции

1. **Сейчас, этап 1:** архив/сопоставление, CSS tokens, локальные шрифты, React/API/contracts, dev proxy, окружение, PostgreSQL, lint/tests/CI. Без готовых страниц и доменных данных.
2. **Этап 2:** модель и ограничения PostgreSQL, единый синтетический каталог; неразрывность записи/согласия и транзакционные ограничения.
3. **Этап 3:** закрытый доступ, DTO каталога и контракт прав; frontend ещё не подменяет API демо-данными.
4. **Этап 4:** доступность, реальное создание/перенос/отмена, 409 и идемпотентность; согласие и защита контактов.
5. **Этап 5:** собрать public components по токенам, затем страницы и booking с API; сравнить с PNG при 360/390/768/1440 px; проверить SEO/ru/kk/доступность.
6. **Этап 6:** собрать admin shell и недостающие экраны по API/матрице прав; согласованные модальные действия и конфликты.
7. **Этап 7:** синтетическая приёмка, контент/лицензия/согласие, законность и эксплуатация до production.

Пункты 1–2 реализованы в разрешённых границах. Перед пунктом 3 работа останавливается; требуется новое подтверждение пользователя.

## Реализация этапа 5

React переносит палитру #005454/#0d6e6e/#faf8ff, локальную Inter/Plus Jakarta Sans, скруглённые светлые карточки, плашки цен, шаги записи и нижнюю mobile-навигацию из Stitch. Desktop/tablet — адаптивные колонки той же системы. Нет фиктивных рейтингов, стажа, ближайших дат, оплаты/WhatsApp/карты/медкарты. Портреты из внешних URL не копируются: до предоставления разрешённых локальных фото — инициалы. Контакты и лицензия явно не утверждены.

Каталог/услуги/цены/длительности/доступность и согласие — из API, не из массивов HTML. Есть страницы карточек, 404, privacy, RU/KK, отдельный PENDING результат. Public изменение записи отсутствует по действующему контракту; показан порядок обращения к сотруднику, без обхода MFA. Все исходники Stitch сохранены. Фактические проверки и ограничения — STAGE-5-REPORT.md.
