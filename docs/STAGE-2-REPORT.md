# Результат этапа 2

Дата: **05.11.2026**. Этап 2 завершён; работа остановлена перед этапом 3. Данные только синтетические. Дизайн, frontend и исходники Stitch не изменены. Auth, новые HTTP API и интерфейсы не добавлялись.

## Реализовано

- 11 Prisma-моделей README, 5 enum, UUID PK, составные ключи/связи, RESTRICT FK, индексы, timestamptz и Decimal snapshots.
- Две транзакционные миграции: начальная Prisma-модель и ручные ограничения PostgreSQL. Установлен btree_gist; exclusion constraints защищают от пересекающихся записей одного врача и пересекающихся рабочих интервалов.
- CHECK для длительностей, точного окончания, конечных рабочих границ, цен (включая запрет NaN), контактов/обезличивания, version, нормализации email, состояния MFA/сессии, согласий, ключей повторов и формы audit metadata.
- Неизменяемость опубликованного текста/доказательства согласия, уникальность текущей версии, отложенная проверка обязательного согласия при commit; аудит append-only для UPDATE/DELETE.
- Внутренний сервис с общими PostgreSQL-блокировками: расчёт времени, создание, рабочие интервалы, перенос, статусы, деактивация врача/назначения и изменение цены/длительности услуги.
- Идемпотентность: advisory lock, уникальный хеш ключа, HMAC параметров, TTL, повтор до проверки занятости и одна транзакция записи/согласия/ключа.
- Ограниченные повторы сериализации/дедлока, безопасная классификация фактических ошибок PrismaPg; остальные ошибки не маскируются как занятый слот.
- Синтетический seed без пациентов/записей и без пригодного для входа пароля; активных сотрудников и сессий не создаёт.

Архитектура, внутренний контактный контракт, порядок блокировок, команды и границы гарантий подробно описаны в [DATABASE.md](DATABASE.md).

## Отдельно: непроверенное и оставшиеся риски

1. **Нет production-авторизации/RBAC и HTTP booking API.** Сотрудники/сессии пока только модели; реальные handlers должны использовать этот сервис. Полный audit actor, rate limits, CSRF, безопасный public DTO и HTTP 409 — последующие этапы.
2. **Production privacy ещё не готов.** Контакты приходят только как доверенный SealedContacts; проверка/нормализация имени и телефона, серверный fingerprint, постоянные ключи, их хранение/ротация/восстановление и применимость криптосредств РК требуют следующей реализации. Тестовый AES-GCM helper нельзя подключать к реальной форме.
3. **Прямой административный SQL может обойти сервисные бизнес-правила** рабочего расписания, активности, version и статусов. БД гарантирует конкретные FK/CHECK/exclusion/consent, но не подменяет сервис. Минимальные production-роли, запрет произвольных ORM-writes в handlers и разграничение миграций/приложения ещё предстоят.
4. **Нагрузка и отказоустойчивость не подтверждены для production.** Проверены 20 конкурентных попыток и реальные ошибки транзакций; не проводились capacity test, failover, сеть около commit, RPO/RTO и backup/restore.
5. **Нет retention/purge/очистки TTL и процесса отзыва данных.** Истечение idempotency key проверяется, но очистка по утверждённой политике — этап 7. Append-only не защищает от владельца БД с TRUNCATE/drop. При аварийном убийстве тестового runner может остаться его временная БД.
6. **Не подтверждены реальные реквизиты, цены/длительности/назначения, переводы, текст согласия и инфраструктура Казахстана.** Seed намеренно не годится для работы с пациентами. Юридическое соответствие не объявляется.

Эти пункты не скрыты как выполненные требования этапов 3–7. Реальных данных нет, публикации нет. **Следующий этап 3 не начинать без нового подтверждения пользователя.**
