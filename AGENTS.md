# Инструкции для работы в clinic

## Текущий этап и разрешённый объём

Этапы 1–3 реализованы. Текущая граница — ожидание подтверждения этапа 4. Argon2id, одноразовая CLI ADMIN, MFA, cookie-сессии, CSRF, backend RBAC, API каталога/сотрудников и audit проверены локально на синтетических данных. Актуальные гарантии/риски — `docs/AUTH.md`, `docs/DATABASE.md`; результаты — `docs/STAGE-3-REPORT.md`. Не начинать этап 4 без подтверждения.

Исходная основа этапа 1 уже создана и проверена: workspaces, инструменты, минимальные web/API и PostgreSQL. Она сохранена, не пересоздавать её и не менять версии стека без причины.

Не создавать HTTP API записи/расписания этапа 4, формы и админ-панель. Не подключать реальные данные, внешние сервисы и deployment. Сохранить дизайн, каркас и ядро бронирования. Применённые миграции не редактировать.

Для защищённых операций использовать `AuthService.withSession`: актуальная роль/сессия проверяются в той же транзакции. Staff management: advisory (75003,1) → staff UUID по порядку → session → doctor/service. Каталог меняется через общие `booking/catalog-mutations`. При подключении booking HTTP потребуется согласованная композиция auth и существующей booking-транзакции, без обхода lock-протокола. MFA обязателен обеим ролям; секреты/пароли выдаются только offline CLI, не через HTTP. Настройки ключей/origin не возвращать frontend. Runtime-роли БД, proxy/TLS, cleanup и ротация ключей ещё требуют production-приёмки из AUTH.md.

Интеграционные тесты используют только созданную самим runner БД с именем `clinic_test_<32 hex>`. Запрещено выполнять reset/drop/truncate рабочей `DATABASE_URL`; миграции рабочей синтетической БД применяются только `migrate deploy`. Контакты в сервис передаются уже запечатанными; production-шифрование и управление ключами остаются этапом 4/7.

Референс — `design-reference/stitch_premium_medical_clinic_portal/`; план переноса — `docs/DESIGN-INTEGRATION.md`. Оригиналы не исправлять и не импортировать в runtime. Единый источник бизнес-данных — PostgreSQL; запрещено копировать JS-массивы, alert-успехи и данные пациентов из HTML.

## Источник решений

- Начинать с `README.md` и `TASKS.md`. README содержит проектируемую архитектуру, модель данных, API и допущения; TASKS — этапы и критерии приёмки.
- Исходное состояние 04.11.2026: пустая директория, нет кода и Git-репозитория. Не утверждать, что будущие команды или тесты уже существуют.
- Стек: React + Vite + TypeScript; Node.js + Express + TypeScript; PostgreSQL + Prisma. Не заменять его Next.js, другой СУБД или сервисом со встроенной несовместимой БД без решения пользователя.
- Сохранять модульный монолит и монорепозиторий. Не добавлять микросервисы, очереди и внешние интеграции без конкретного обоснования.
- Изменение поведения, состава данных или доступа сначала отражать в плане и критериях приёмки. При конфликте с более поздним явным указанием пользователя соблюдать его указание и актуализировать документы.

## Правила реализации после подтверждения

- TypeScript strict на frontend/backend; явные типы на границах, `unknown` и проверка для непроверенных данных. Не скрывать ошибки через `any`/массовые type assertions.
- Слои backend: router/middleware/controller/service/repository. Бизнес-правила и транзакции — в service; HTTP и UI не обращаются напрямую к БД.
- DTO/Zod public и admin разделены. Не возвращать ORM-модели напрямую и не применять request body к Prisma без allowlist.
- React компоненты организовывать по страницам и функциям. Серверные данные — через query layer, формы — с клиентской валидацией, обязательна повторная валидация на сервере.
- Пользовательские даты отображать в IANA-зоне клиники. В БД — `timestamptz`, в API — ISO 8601 с offset/UTC. Не полагаться на часовой пояс ОС/браузера.
- Деньги — Decimal/numeric в KZT; сериализовать согласованной десятичной строкой. Время окончания, длительность и цена записи вычисляются сервером, snapshots сохраняются.
- Согласованные переводы ru/kk, адаптивность, доступность, SEO и состояния ошибок входят в готовность функции.
- Точные версии и команды фиксировать только после проверки совместимости и появления manifest/lockfile. Не выдавать предполагаемые команды за проверенные.

## Инварианты БД и календаря

- Пересекающиеся неотменённые записи одного врача запрещаются PostgreSQL exclusion constraint с `btree_gist` и `tstzrange(..., '[)')`. Нельзя заменить его только проверкой SELECT, mutex процесса или `UNIQUE(doctor_id, starts_at)`.
- Рабочие интервалы врача также не пересекаются. Запись целиком помещается в рабочий интервал и не пересекает перерыв.
- Создание, перенос, отмена, изменение расписания и деактивация врача/назначения услуги координируются общей блокировкой строки врача. Порядок: только при создании сначала advisory lock ключа повтора; затем врачи по UUID → услуги по UUID → согласие/запись. Изменение услуги не захватывает врачей после услуги. Все новые mutating endpoints должны вызывать готовый сервис, а не обходить этот протокол.
- Уже применённые миграции не переписывать. Integration suite всегда применять ко всей истории с нуля: проверки каталогов PostgreSQL должны обнаруживать потерю ручных ограничений в новых миграциях.
- Перенос атомарный, при конфликте исходная запись сохраняется. Admin-изменения используют `version`; устаревшее состояние даёт 409.
- Заявка, согласие и ключ идемпотентности создаются в одной транзакции. Никаких внешних сетевых вызовов внутри транзакций.
- Каталог с историческими ссылками архивировать, не удалять каскадом. Изменение услуги не переписывает существующие snapshots.
- Неподдержанные выбранной Prisma schema ограничения оформлять ручным SQL в миграциях, проверять применение на чистой БД и наличие ограничений. Не использовать `db push` для production и не удалять ручной SQL при генерации следующих миграций.
- На занятой интервал — 409 `SLOT_UNAVAILABLE`; другие ошибки не скрывать под этим кодом. Отдельно проверить mapping SQLSTATE через выбранный adapter.

## Доступ и персональные данные

- Собирать только разрешённые контакты и выбор записи с согласием. Не добавлять диагнозы, ИИН посетителя, дату рождения, медицинские документы, жалобы, свободные заметки или вложения.
- Не добавлять карточку пациента и поиск по телефону без отдельного согласования. Имя и телефон зашифрованы; ключи отдельно от БД. Шифрование — через проверенные библиотеки и согласованные криптосредства.
- Ни реальные данные, ни production dumps не использовать в примерах, seed, тестах, скриншотах и CI. Только синтетические fixtures.
- Не писать PII, session cookie, пароли, MFA-секреты, ключи и тело заявки в URL, логи, аудит, аналитику и сообщения об ошибках. Не логировать body/headers по умолчанию.
- Не хранить session token, имя и телефон в localStorage. Форма — в памяти текущей страницы; admin/booking API — no-store.
- Авторизация/проверка роли выполняется API на каждом admin-запросе; скрытие кнопки не является контролем доступа. ADMIN и RECEPTIONIST имеют разные права согласно README.
- Cookie-сессии: серверное хранение хеша токена, HttpOnly/Secure/SameSite, CSRF и проверка Origin, конечные сроки жизни, отзыв при изменении доступа. MFA обязателен до production.
- Никаких общих или предустановленных паролей. Учётные записи создаются контролируемой процедурой, публичной регистрации сотрудников нет.
- Персональные данные и связанные runtime-хранилища планировать в Казахстане. Не подключать иностранные обработчики, карты, captcha, мониторинг, SMS/email и CDN к потоку записи без проверки географии, договоров и передачи данных.
- Юридический обзор по официальным источникам — в README. Не объявлять проект соответствующим всему законодательству только по наличию checkbox, HTTPS и этого плана. Перед production должны быть закрыты юридические и эксплуатационные задачи из TASKS.
- Не назначать произвольные сроки хранения «по закону». Применять утверждённый регламент удаления, связанных журналов и backup; soft delete не равен удалению данных.

## Проверка и завершение этапа

- Выполнять минимальные достаточные проверки с реальными критериями. Для ограничений PostgreSQL и гонок обязательны интеграционные тесты на PostgreSQL, а не SQLite или моки.
- Для записи проверять конкурентные запросы, перекрытие разной длительности, соседние интервалы, изменение расписания, перенос, отмену и идемпотентный повтор.
- Для доступа проверять 401/403, CSRF, IDOR, отзыв сессий и отсутствие утечки в public DTO/логах. Для UI — mobile/desktop, ru/kk, ошибки и доступность.
- Не помечать задачу выполненной без проверяемого результата. В TASKS фиксировать фактический статус; в отчёте назвать, что изменено, что проверено и что остаётся.
- На этапе 1 проверять реальные команды lint/format/typecheck/tests/build, ответы API и development proxy, доступность локального PostgreSQL и конфигурацию Prisma. Проверки бизнес-ограничений относятся к этапу 2 и не должны заявляться как выполненные.
- Не публиковать и не подключать реальные данные в рамках планирования. После разрешённого этапа останавливаться на согласованной границе, без самовольного расширения объёма.
